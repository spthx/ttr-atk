# 『ロマンシング サ・ガ3』トレード再現基準

- 調査日: 2026-08-22
- 対象: SFC版とリマスター版の公開プレイ映像、任天堂公式説明
- 用途: 「タタルの大繁盛商店」の仕様判断、実装、回帰監査
- 数値正本: [`rs3-trade-regression-baseline.json`](./rs3-trade-regression-baseline.json)

この資料は「雰囲気が近い」という主観だけで修正しないための根拠台帳である。観測した事実、映像から測った値、実装上の推測を分ける。原作画面は4:3固定なので、縦持ち・横持ち対応は原作の幾何を壊さない範囲の実装判断とする。

## 1. 証拠の区分

- **O — Observation:** フレームから直接確認できる事実
- **M — Measurement:** 公開動画の表示時刻や画面比率を採寸した値
- **I — Inference:** 複数フレームと実装制約から導いた推測
- **U — Unverified:** 資料候補だが、まだフレーム採寸していないもの

「第1部＝常に低い山」ではない。シナリオ段階と積載状態は別軸で、第1部後半にも画面上端へ届く山が出る。序盤感は描画上限で強制せず、少ない資金源、小さい取引額、少ない連続ページで作る。

## 3. コインと台座の再現仕様

### 配置

- **O:** 1ページは18アンカー、奥から `[4, 5, 5, 4]`。
- **O:** 左右は同じ幾何の鏡像。
- **I:** 少量は手前中央から連続した塊として置く。映像の安定状態に合い、後方の浮遊錯視を防ぐための移植ルールである。
- **O:** 18アンカーを面として埋めた後、同じ位置を縦へ伸ばす。
- **O:** 巨額でも上面は18位置由来の密な面を保ち、ランダムな粒子山へ崩さない。

### 落下単位

- **O:** 薄い金貨1枚ではなく、上面楕円、金色側面、複数の水平仕切りを持つ短い円柱状の金貨束。
- **M:** YouTube再圧縮後でも1束に概ね8〜10本の水平仕切りが読める。
- **I:** 実装は「最低8枚に見える束」を保守的な下限にする。仕切り本数から原作の正確な枚数は断定しない。
- **O:** 姿勢を保って目的アンカーへ直線的に落ち、大きく跳ねない。
- **O:** 安定状態として孤立した薄い1枚を残さない。

### 台座と接地

- **O:** 食器の皿ではなく、上面が大きい楕円で、縦筋のある厚い低円柱。
- **M:** 台座直径は束幅のおよそ `6.5 ± 0.7` 倍。
- **I:** 現実装は18アンカーの外周余白と横画面の占有率を守るため`7.45`束幅を採用する。原作値そのものではなく、縦横可変画面へ移植するための回帰値としてJSONへ固定する。
- **O:** コインの底と台座上面の間に背景色の水平ギャップを作らない。
- **O:** 手前列は台座の前壁へ少し隠れ、台座へ置かれていることが分かる。
- **O:** リマスターの多ページ下降では、完成山と台座を同じ移動体として扱う。

## 4. 時間基準

| プリセット | 1ページ | 9波を採用する場合の1波 |
| --- | ---: | ---: |
| SFC優先 | 1.40〜1.55秒 | 0.15〜0.17秒 |
| リマスター優先 | 0.52〜0.68秒 | 0.055〜0.075秒 |

現在の標準はユーザー指示どおりSFC優先で、9波×165ms＝1.485秒。30fpsでは1波を約5フレーム見せる。省モーション時だけ短縮経路を使う。

音声は実況、BGM、配信処理を分離できていないため、SFC原音の発音間隔を認証済み値にはしない。既存の許諾済みローカル録音を1本のcached loopとして使い、99msの細かな接触音を165msの外側の束ビート内へ重ねる。音の原作認証には無実況の正規キャプチャが必要。

## 5. ゲーム展開から学ぶこと

SFC第1部の公開映像では、概ね次の順で学習と成長が進む。

1. 02:03前後に最初の安価な物件を選ぶ。
2. 02:17から少ない自社資金を一手ずつ積み、コインと背景ストライプの意味を覚える。
3. 03:13前後には再挑戦とグループ要求が入り、資金源を選ぶゲームへ広がる。
4. 04:32以降、次の物件へ移り、勝利した物件が次の資金源になる循環を見せる。
5. 06:44前後、トレード技の習得・使用で、単純な自社資金連打から戦術へ移る。
6. 08:01以降、複数の資金源を束ねることで山と金額が急拡大する。
7. 14:36以降は約1億規模の強敵と長く競り、17:21に成功、17:52に第1部完了。

序盤UIは詳細な内部式を最初から見せるより、「次に攻める都市」「初心者向けの相手」「勝利後に増える人脈・収益」「開始手数料」を先に出す。企業連合や詳細フィルタは必要になってから開く。原作の学習順と同じく、最初の一手、勝利、新しい資金源、グループ、技、強敵の順に情報を開示する。

後半のインフレ感は次で作る。

- 相場の桁が上がるほど、同じ投入比率でも柱の上限を増やす。
- 所有物件、地域グループ、同盟、技が増え、1回の行動で動く資金と連続波数が増える。
- 序盤にも1束あたり8枚以上の物理感は保ち、単に小さな1枚へ縮めない。
- シナリオ章そのものをレンダラーの高さ制限へ使わない。

## 6. 現実装の判断

- 描画器はCanvas2Dを維持する。固定18アンカー、2枚のラスター素材、2Dの前後関係にはThree.jsのscene graph、shader、WebGL初期化が不要で、Canvas2Dの静的キャッシュの方が軽い。
- 台座: `src/assets/battle/capital-pedestal-sfc.png`
- 金貨: `src/assets/battle/capital-coin-sfc.png`
- 1論理unitは最低8枚の金貨束として描く。
- 18アンカーと前中央からのfill orderを固定する。
- 前壁を後から重ね、コイン根元を隠して接地させる。
- SFC標準は165ms×9波。資金、所有率、勝敗、AI、command rechargeはpresentation clockと分離する。
- 30fps時DPR上限1.5、60fps時DPR上限2、静止山はキャッシュし、アニメーション中はincomingと前壁だけを追加描画する。
- 390×844、844×390、PC wide、DPR 1／1.25／1.5／2で同じ18アンカーと接地を保つ。

Three.js／WebGLへ置き換えないのは消極策ではない。現在の描画は固定18アンカー、2枚の透過PNG、平面の前後マスクだけであり、静止山をオフスクリーンCanvasへキャッシュすると、毎フレーム必要なのは落下束と前壁の合成だけになる。3Dカメラ、ジオメトリ、マテリアル、shader、WebGL contextを増やしてもdraw対象は減らず、初期化・VRAM・低価格端末のcontext loss対策が増える。将来、自由カメラ、3D照明、数百個の独立剛体が本当に必要になった時だけ再評価する。

## 7. 回帰不変条件

1. アンカー数18、行 `[4,5,5,4]`。
2. 最小settled unitは8枚以上の束。薄い1枚を保持しない。
3. 前中央から積み、1束でも台座前壁と重なる。
4. コイン底と台座上面の背景ギャップはAA込み最大1 device px。
5. 左右中心は同一viewportで鏡像誤差1 logical px以内。
6. SFC標準ページは1.40〜1.55秒。
7. 金額確定後の残留演出を許し、二重加算しない。
8. 論理上readyなら、残留落下中でも次コマンドUIを表示できる。
9. 演出時間を変えても資金・所有率・勝敗・AI結果を変えない。
10. 縦横で台座、18アンカー、前後関係を変えず、UIだけを再配置する。
11. 各active列で、完全着地したincoming束の上端とsettled後の山頂を一致させる。巨額時も着地後だけ柱を伸ばさない。

静的検査は `npm run check:capital-contact`、ブラウザの目視は上記fixtureと実戦初戦の両方で行う。regex合格だけで「見えた」と判定しない。
